# Agent-native access

GroundControl exposes a narrow remote MCP surface at `/mcp`. External agents receive typed infrastructure capabilities, not shell access or infrastructure credentials.

## Connect

1. Add `https://<your-groundcontrol>/mcp` to a compatible remote MCP client.
2. The client discovers GroundControl OAuth through RFC 9728 protected-resource metadata.
3. GroundControl authenticates the operator, requests OAuth consent, and lets the operator choose the exact deployments the client may see.
4. The client receives short-lived bearer access plus a rotating refresh token when `offline_access` is granted.

OAuth uses Authorization Code + S256 PKCE. Client ID Metadata Documents are supported; dynamic client registration remains available for compatibility.

## Capability surface

Read:
- `deployment.list`
- `deployment.inspect`
- `deployment.logs`
- `deployment.health`
- `deployment.config.check` — exact-key presence/status only; never returns values
- `operation.get`

Write (administrator-approved `deployment:redeploy` scope):
- `deployment.redeploy`
- `deployment.restart`
- `deployment.source.deploy`
- `deployment.build_publish`
- `deployment.release`

`deployment.list` and `deployment.inspect` report runtime capabilities for each approved deployment. Each mutation reports `supported`, `authorized`, `available`, and an explanation when unsupported. Availability does not depend on the deployment being marked managed rather than tracked.

| Runtime | Restart | Redeploy | Linked source deploy | Build/publish and digest release |
| --- | --- | --- | --- | --- |
| Compose, including configuration generated by a template | Yes | Yes | With a linked GitHub repository | Build needs linked GitHub; release needs a successful image build |
| Standalone Docker container | Yes, exact enrolled container | Captured mount-free local-image recipe | Unsupported | Unsupported |
| Static site | No container to restart | Saved build/publish recipe | Saved recipe and linked GitHub repository | Unsupported |

A source repository does not need a Compose file when GroundControl has generated the deployment's Compose configuration. Source import or granting access does not invent a missing deployment recipe.

New mount-free local-image launches bind an explicit private port and capture the immutable image, port, ownership and a fingerprint of the complete Docker configuration without persisting container environment values. Standalone redeploy recreates that same image; it does not pull an updated tag. It inspects a prepared replacement before stopping the original, rejects configuration drift, preserves the private port, and verifies the replacement runtime. Confirmed replacement failure restores the original and verifies its prior running state. Lost replies remain uncertain with exact container IDs for reconciliation. Successful recreation keeps the stopped original and its writable layer for operator recovery; removing retained containers is an explicit operator task. Imported or older containers without a captured recipe, dynamic port bindings, mounted images and custom networks remain restart-only because their launch/storage intent cannot safely be inferred.

Docker and source-workspace operations use the recorded target. In Desktop mode they use the mounted Docker socket and workspace, without requesting access to the computer's native operating system. Remote deployments continue to use their own recorded host.

New static template deployments retain their build command and output directory plus a versioned recipe backup. A missing canonical recipe can be recovered only from explicit saved choices bound to the same source and publish paths; conflicting or absent choices are not guessed from template defaults or package scripts. Older records without either recipe still require the operator to restore those choices. Private build commands are omitted from release evidence. Static publishing updates the saved document root and keeps a previous copy; it does not recreate proxy or DNS configuration.

Health distinguishes evidence from absence of evidence: `runtime.healthy` and top-level `healthy` can be `null` (unknown). Static sites have no container runtime, so a successful public HTTP check can establish health. Docker health uses the enrolled container or exact Compose project/file and honors Docker healthcheck failures. A missing host, inspection failure, skipped public check, or unsupported runtime is not reported as verified healthy. Public checks do not follow redirects; only a 2xx response counts as success. An operation can successfully apply files while explicitly reporting `publicVerified: false` and `healthy: null`.

No MCP tool exposes SSH credentials, provider secrets, raw terminal access, or generic command execution. Configuration inspection is exact-key only and returns `configured`, `missing`, or `unmanaged` metadata without masked or partial secret values.

## Durable mutations

Every mutation requires an idempotency key and returns an `AgentOperation` immediately. A key is bound to its grant, deployment, operation type, input, and runtime identity. Repeating identical input returns the original operation, including failed or uncertain outcomes; reusing it for different work fails. Concurrent identical submissions converge on one operation.

Before execution, GroundControl rechecks the grant, administrator status, scope, deployment membership, runtime capability and recorded identity. Host, paths, Compose project and container identity come from that approved deployment, never the currently active host. Detached evidence is recorded per operation. A duplicate runtime dispatch does not execute twice.

Typical lifecycle:

```
pending -> running -> verifying -> success
                   \-> failed
running + GC restart -> uncertain
```

Self-hosted detached redeploys survive the calling agent disconnecting and are reconciled from GroundControl's deployment evidence. A GroundControl restart during a non-detached mutation is not replayed automatically because the external side effect may already have occurred; the operation becomes `uncertain`.

## Revocation

The Agents workspace lists authorized MCP clients and their exact workload grants. Revoking a grant:
- revokes current access/refresh tokens;
- cancels queued operations that have not started;
- prevents future MCP reads/writes.

An already-running mutation is not force-killed solely because a grant is revoked; GroundControl continues recording its outcome so the control plane does not lose operational evidence.

## Current acceptance milestone

A release is agent-ready when a remote client can:

1. connect to GroundControl using OAuth;
2. inspect an approved deployment;
3. check its health;
4. request a redeploy;
5. receive an operation id immediately;
6. disconnect;
7. reconnect using refresh access;
8. read the operation's verified success/failure evidence;
9. remain unable to see or mutate deployments that were not granted.
