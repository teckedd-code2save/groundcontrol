# First-deployment MCP acceptance

Source change: explicit `deployment:create` host consent, including OAuth consent with zero
existing deployments; create_options/plan/create tools; atomic target reservation and same-grant
durable creation → build/publish → digest release; shared UI/MCP launch service.

Locally executed on 2026-11-26:

- Complete Vitest suite: 733 tests across 109 files passed.
- Additional final focused run: 16 creation/runtime tests passed after locking reserved targets
  against runtime operations until preparation finishes.
- Native OAuth recovery additionally passed 28 focused MCP/OAuth tests: creation advertises the
  complete required scope set in its HTTP challenge, so consent does not loop on a partial grant.
- Production Next.js build passed, including TypeScript. Existing QA-harness file-tracing warning.
- Lint passed with zero errors and 18 existing warnings. The lint configuration now scopes React
  rules to supported files and permits CommonJS require in .cjs files; a non-hook server helper
  was renamed to avoid React hook misclassification.
- Additive migration rehearsed on an existing synthetic grant: resources/scope unchanged,
  creationHosts defaults to [], SQLite integrity_check returned ok.

The flow test calls the authenticated MCP HTTP endpoint with a real disposable SQLite database,
then the actual worker, internal creation route and shared template launch service. GitHub reads,
Git checkout and host commands are substituted at their external boundaries. It proves readable
same-grant delivery operations, idempotency (including concurrent calls and uncertain outcomes),
wrong-host denial, revocation before dispatch and after checkout, directory collision handling,
encrypted credential persistence, duplicate-dispatch rejection and empty-inventory consent.
It does NOT prove SSH/Docker/Caddy/GHCR, real Actions publication, DNS/TLS or application behavior.

Live acceptance still required after an authorized rollout:

1. Back up/quiesce the GC database and configuration using the supported upgrade process; preserve
   rollback material. Deploy the reviewed GC image by digest and confirm health.
2. Refresh client tool discovery (revision 2026-11-27.create.1). Reconnect with creation, read,
   redeploy and operation scopes, explicitly selecting the intended host. Old grants remain scoped.
3. Use the actual app repository, exact branch SHA, isolated Compose recipe, published loopback
   port and new DNS hostname. Discover options and run plan before create. No existing workloads
   are eligible for adoption by this path.
4. Follow creation, delivery and child release operations. Confirm complete service graph, exact
   running image digests, HTTPS, auth and a database write/read journey.
5. Exercise one authorized subsequent branch update and observe its exact new revision deployed.

Boundaries: configured Linux Docker Compose/Caddy host; GitHub App repository access and registry
access; DNS already pointing to the host. No cloud-host provisioning, DNS/firewall edits, or shared
resource adoption. New random credentials can be generated by key name; external provider secrets
need GC's configuration path. Failed/uncertain creation keeps its reserved target/files for owner
inspection and is never replayed automatically. Database rollback is separate from image rollback.

GC managing Vercel through a provider adapter is future work, deliberately outside this milestone.
Forge's Vercel route uses the provider's supported tools directly. No production state was changed
by this local validation.
